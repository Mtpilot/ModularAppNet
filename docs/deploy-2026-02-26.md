# Донастройка mauth под nginx — 26 февраля 2026

Репозиторий был перенесён в `/etc/app/mauth` и смержен с веткой другого разработчика.
После мержа стек не запускался. В этом документе описаны все сделанные изменения,
причины и как это работает.

---

## 1. Имена контейнеров и сеть `shared-network`

**Файл:** `docker-compose.yml`

**Что изменено:**
- Добавлен `container_name: mauth_app/mauth_postgres/mauth_seq/mauth_jaeger` для каждого сервиса
- Добавлена сеть `shared-network` (external) и все сервисы подключены к ней

**Почему это работает:**

Nginx-shared резолвит апстримы по имени контейнера. В `/etc/nginx/conf.d/projects/locations/mauth.conf`
прописаны `mauth_app:8080`, `mauth_seq:80`, `mauth_jaeger:16686`, `mauth_front:80`.
Без явных `container_name` docker compose генерирует имена вида `mauth-shipping-modular-monolith-1`,
которые nginx не найдёт.

Сеть `shared-network` — общая сеть, в которой находится контейнер `nginx-shared`.
Без неё nginx и приложение находятся в разных сетях и не видят друг друга.

## 2. Учётные данные PostgreSQL и строка подключения

**Файлы:** `docker-compose.yml`, `ModularMonolith.Host/appsettings.json`

**Что изменено:**
- `POSTGRES_USER=admin` → `POSTGRES_USER=postgres`
- `POSTGRES_PASSWORD=admin` → `POSTGRES_PASSWORD=secretpassword`
- Строка подключения: `Server=localhost;Port=5450` → `Server=postgres;Port=5432`

**Почему это работает:**

Внутри docker-compose сервисы обращаются друг к другу **по имени сервиса** (`postgres`),
а не по `localhost`. Порт `5432` — внутренний порт контейнера postgres, `5450` — это
проброс наружу для внешних клиентов (например, DBeaver). Приложение работает внутри
docker-сети и должно обращаться на внутренний порт.

**Примечание про volume:** если `docker_data/pgdata` уже заполнена данными старой БД
(с `admin/admin`), простая замена переменных окружения не создаёт нового пользователя —
postgres не переинициализирует уже существующую БД. В этом случае нужно либо удалить
`docker_data/pgdata` и поднять заново (чистая БД), либо создать пользователя вручную через psql.

## 3.1. `ASPNETCORE_ENVIRONMENT=Development`

**Файл:** `docker-compose.yml`

**Что изменено:**
- `ASPNETCORE_ENVIRONMENT=Production` → `ASPNETCORE_ENVIRONMENT=Development`

**Почему это работает:**

Swagger middleware в ASP.NET Core подключается только в `Development` окружении
(стандартный паттерн `if (app.Environment.IsDevelopment()) { app.UseSwagger(); ... }`).
В `Production` Swagger отключён из соображений безопасности. Без этой переменной
обращение к `/swagger/...` давало бы 404.

## 3.2. `MauthServerDocumentFilter` — правильный base URL в Swagger UI

**Файлы:**
- `Common/Modules.Common.API/Swagger/MauthServerDocumentFilter.cs` *(новый файл)*
- `Common/Modules.Common.API/DependencyInjection.cs`

**Что изменено:**

Создан класс `MauthServerDocumentFilter`, реализующий `IDocumentFilter` (Swashbuckle):

```csharp
public sealed class MauthServerDocumentFilter : IDocumentFilter
{
    public void Apply(OpenApiDocument document, DocumentFilterContext context)
    {
        document.Servers = new List<OpenApiServer>
        {
            new OpenApiServer { Url = "/external/mauth" }
        };
    }
}
```

В `DependencyInjection.cs` зарегистрировано:

```csharp
options.DocumentFilter<MauthServerDocumentFilter>();
```

**Почему это нужно:**

Swagger UI при нажатии «Try it out» отправляет запросы на URL, указанный в поле `servers`
OpenAPI-документа. По умолчанию Swashbuckle ставит `/`, поэтому UI слал запросы на
`https://ru01-vm23.gal.lan/api/users/register`. Nginx не матчил этот путь ни с одним
location и отдавал 404.

Nginx проксирует mauth только по префиксу `/external/mauth`, поэтому рабочий URL:
`https://ru01-vm23.gal.lan/external/mauth/api/users/register`. Фильтр явно выставляет
этот base URL — и Swagger UI начинает отправлять запросы на правильный путь.

## 4. Сервис `mauth_front` — восстановление фронтенда

**Файлы:** `docker-compose.yml`, `frontend/` *(восстановлена директория)*

**Что изменено:**

Директория `frontend/` была потеряна при мерже. Восстановлена из старого репозитория.
В `docker-compose.yml` добавлен сервис:

```yaml
front:
  image: mauth-front
  container_name: mauth_front
  build:
    context: ./frontend
    dockerfile: Dockerfile
  restart: always
  ports:
    - "8082:80"
  networks:
    - docker-web
    - shared-network
```

**Почему это нужно:**

Nginx уже настроен на `mauth_front:80` в location'ах для `/external/mauth/`,
`/external/mauth/auth_test/`, `/external/mauth/readme-ru.html`. Без работающего
контейнера `mauth_front` эти пути давали бы 502.

`frontend/Dockerfile` собирает `nginx:alpine` образ со статическими файлами:
`index.html`, `readme-ru.html`, `auth_test/`.

## 5. Healthcheck для Seq и `depends_on` для app

**Файл:** `docker-compose.yml`

**Что изменено:**

```yaml
seq:
  healthcheck:
    test: ["CMD-SHELL", "timeout 2 bash -c 'echo >/dev/tcp/127.0.0.1/80' || exit 1"]
    interval: 15s
    timeout: 5s
    retries: 5
    start_period: 60s

app:
  depends_on:
    seq:
      condition: service_started
    jaeger:
      condition: service_started
```

**Почему `curl`/`wget` не работают:**

Образ `datalust/seq:2024.3` не содержит `curl`, `wget` или `nc`. Попытка использовать
`CMD ["curl", "-fsS", "http://localhost:80/"]` приводила к `executable file not found`.

**Почему работает `bash /dev/tcp`:**

`bash` в образе есть (`/usr/bin/bash`). Конструкция `/dev/tcp/host/port` — встроенный
механизм bash для TCP-соединений, не требующий внешних утилит. Команда
`echo >/dev/tcp/127.0.0.1/80` открывает TCP-соединение на порт 80 (UI/API Seq).
Если соединение успешно — возвращает 0, иначе — ненулевой код. `timeout 2` предотвращает
зависание при недоступном порте.

**Почему `start_period: 60s`:**

При наличии существующих данных в `docker_data/seq/` Seq восстанавливает состояние
из диска перед тем как начать слушать порт. На тестах (чистый образ) порт открывается
за ~15 секунд. С данными — дольше. `start_period: 60s` означает: первые 60 секунд
неудачи healthcheck **не считаются** — контейнер не помечается unhealthy, пока не
истечёт этот период. После — начинается отсчёт `retries: 5`.

**Почему `condition: service_started` а не `service_healthy`:**

`service_healthy` означает «не запускать app пока seq не станет healthy». Если healthcheck
seq падает по любой причине — app никогда не стартует. `service_started` означает «дождаться
только запуска контейнера seq», без ожидания healthy. App при старте подождёт seq/jaeger
сам (через retry-логику в Seq-клиенте), и это приемлемо для системы логирования — в
худшем случае первые несколько логов потеряются.

## 6. Обновление PostgreSQL до v18

**Файл:** `docker-compose.yml`

**Что изменено:**

```yaml
# было:
image: postgres:latest
volumes:
  - ./docker_data/pgdata:/var/lib/postgresql/data

# стало:
image: postgres:latest
volumes:
  - ./docker_data/pgdata:/var/lib/postgresql
```

**Почему это сломалось:**

В феврале 2025 `postgres:latest` стал PostgreSQL 18. В v18 Docker-образ изменил
соглашение о расположении данных: теперь данные хранятся в
`/var/lib/postgresql/18/main` (подкаталог с номером мажорной версии).

Старое монтирование `/var/lib/postgresql/data` PostgreSQL 18 видит как «данные
в устаревшем месте» и отказывается запускаться с ошибкой:

```
Error: in 18+, these Docker images are configured to store database data
in a format which is compatible with "pg_ctlcluster"
```

**Решение:** монтировать на уровень выше — `/var/lib/postgresql`. Тогда PostgreSQL 18
сам создаёт подкаталог `18/main` и инициализирует базу.

Поскольку `docker_data/pgdata/` была пустой (данные не накапливались), миграция
прошла без потерь.
